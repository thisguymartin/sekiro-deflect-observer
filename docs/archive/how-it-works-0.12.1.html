How one attack becomes a cue

Sekiro Deflect Observer is code loaded inside Sekiro as a Windows DLL. It watches a locked enemy's animation, classifies the current attack phase, and asks ImGui to draw a HUD during each DirectX 11 frame.

This guide follows the current 0.12.1-preview source. It describes animation evidence, not collision, button input, or a confirmed deflect.

Follow one attack through the whole mod

Start here. Click each numbered handoff. The left side explains what the code does. The right side shows how the data changes before the next part receives it.

Example. The locked enemy advances animation 3000 to 0.42 s. The values below are illustrative, but the objects and handoffs match the current source.

Sekiro game thread

Sekiro updates the enemy first

The game advances its own animation state. Your DLL has not decided anything yet. It is waiting inside the same process for the researched animation function to run.

Keep this boundary clear. The game owns the animation. The mod only observes a copy of its state.

What exists now 
// Inside Sekiro memory
enemy.animation = {
  id: 3000,
  time: 0.42,
  owner: locked_enemy
}
Animation hook

The hook copies a completed batch

The detour reads the 224-byte animation batch twice. Matching reads mean the copy stayed stable. It stores one fresh snapshot, then calls Sekiro's original function.

The hook captures a better timestamp. It does not replace the game function and it does not classify the attack.

New evidence 
HookSnapshot {
  animation_id: 3000,
  animation_time: 0.42,
  captured_at: T + 2.1 ms,
  source: EventBatch
}
observer-reader thread

The worker joins facts into one Target

On its next loop, the worker validates the current lock and animation owner. It combines the hook snapshot with enemy identity, health, positions, facing, and camera data.

Downstream code receives one validated object. It does not repeat pointer walks or guess whether the animation belongs to this target.

Published model 
Target {
  handle: 0x…A410,
  model: 1550,
  npc_param: 155000,
  animation: #3000 @ 0.42 s,
  capture_source: EventBatch
}
attack::classify

The classifier matches facts to a Phase

The classifier searches the generated rows for model 1550, its NPC variation, animation 3000, and time 0.42. A matching row says which attack phase is active.

A Phase is game evidence. It says what the animation data supports before HUD preferences change the presentation.

Classification result 
Phase {
  kind: Parryable,
  start: 0.38,
  end: 0.51,
  animation_time: 0.42,
  index: 0
}
timing::Engine

The engine converts evidence into a HUD answer

Default incoming mode turns the parryable Phase into an active PARRY decision. It carries progress and capture evidence forward. Unknown or stale input produces a safe neutral or hidden result.

This is the policy boundary. A Phase describes the attack. A Decision describes what the interface may show.

Renderer-facing answer 
Decision {
  state: Active,
  response: Parry,
  progress: 0.31,
  capture_source: EventBatch,
  contact: None
}
DX11 render callback

ImGui submits the visible cue

The render callback checks focus, freshness, visibility, and invalidation generation once more. It computes cue bounds and adds the rail, marker, label, and emblem to the current DirectX frame.

The render log proves that draw commands were submitted. It cannot prove that the monitor presented the pixels or that a deflect succeeded.

Frame record 
RenderSample {
  status: Drawn,
  label: "PARRY",
  bounds: [x, y, w, h],
  generation: 42
}

// Submitted to this frame
Step 1 of 6

One rule explains the architecture. Each stage receives a narrower, safer answer than the stage before it. Raw memory becomes a validated target, then a classified phase, then a display decision.

Four execution lanes share the work

The DLL runs inside Sekiro, but its jobs do not all happen at the same time. Read each lane left to right. Arrows inside a lane show order. Shared objects carry results between lanes.

Startup thread
verify sekiro.exe→ hash executable→ install hooks
Game thread
animation function runs→ hook copies batch→ original function continues
Worker thread
validate lock→ build Target→ publish CueState
Render thread
read CueState→ make Decision→ submit ImGui draw commands
F11 side path
remember original speed→ write slowed speed→ restore exact original
  • Normal observation and drawing
  • Optional game-memory write

The main path reads. Only the F11 practice adapter writes game memory. It temporarily changes one enemy animation-speed value and restores the exact original. The HUD, classifier, and diagnostics cannot perform that write.

Events, polls, and frames are different things

The same 32 milliseconds can contain one animation event, four worker polls, and two rendered frames. They are independent schedules. The example timeline below shows why one does not replace another.

The event captures timing

The hook runs when Sekiro consumes a completed animation batch. It copies stable evidence and immediately returns control to the game.

The worker builds context

The next poll joins that evidence to the current lock, actor, camera, identity, config, and ownership checks.

The frame displays the latest safe answer

The next render may arrive before or after a worker poll. It uses published state and rejects data older than the freshness window.

Why both a hook and polling? The hook supplies a precise animation-batch observation. Polling resolves everything around it. If the hook is active but has no fresh snapshot, the mod refuses to reuse an older polled animation.

The types form a chain. They do not all have equal jobs. Follow the arrows to see raw observation become a safe interface answer.

What happens during one visible frame

The renderer has a strict job. It reads the latest published answer, rejects unsafe state, submits geometry, and leaves file writing to the worker.

Observer
1. Begin a hidden RenderSample

The frame counter advances. The default record assumes nothing will be drawn until every gate passes.

Lifecycle
2. Capture the invalidation generation

Target loss, owner changes, focus loss, and visibility changes can make previous geometry unsafe.

CueState
3. Lock, copy, unlock

The renderer clones the fresh target, settings, profiles, and practice status. It does not walk game memory or parse files while holding the mutex.

Engine
4. Produce a Decision

Incoming mode classifies the phase directly. Legacy mode can estimate intervals only when the animation clock has a stable rate.

Lifecycle
5. Check the generation again

If another thread invalidated the target during this frame, rendering stops before submitting stale geometry.

ImGui
6. Draw and queue the record

cue_draw::draw submits the rail, marker, label, and emblem. A bounded queue sends the record back to the worker for later CSV writing.

The mutex is not the frame. It protects the handoff long enough to copy state. Layout, drawing, and disk logging happen after the renderer releases it.

The default HUD follows attack phases, not button timing

The default incoming path uses the current animation phase directly. It shows what response the extracted game parameters support and whether that phase is still winding up or already active.

With incoming_cues = false, the engine estimates animation speed from progressing captures. It projects at most 25 ms, checks coarse reach, and can produce preparation, actionable, and expired states. A calibrated profile may add a contact proxy and preferred instant. Freshness matters. A lock observation and an animation capture both expire after 50 ms. A fresh lock with stale animation can show neutral LOCKED. It cannot keep an old attack actionable.

Practice mode shares facts, not HUD decisions

F11 practice asks the raw classifier whether the current phase is eligible. It does not ask whether a PARRY or JUMP label is visible. This keeps alert preferences from changing gameplay speed.

What makes an attack eligible, and what starts restoration?

Parry, sweep, and thrust phases can qualify. Grabs, unknown phases, no-parry phases, stale samples, and frozen animation clocks stay at normal speed.

Attack end, focus loss, a hidden HUD, target switch, factor change, or F11 disarm starts restoration. Failed reads or writes remain in RESTORING for another worker tick. A conflicting external write moves practice to PAUSED instead of overwriting it.

A short glossary for your next code-reading pass

These terms recur across the source and tests.

What do DLL, DirectX 11, and ImGui mean?

A DLL is a compiled library that the loader places inside Sekiro's process. DirectX 11 is the graphics API the game uses to submit frames. ImGui is the interface library the mod uses to add its own draw commands to those frames.

What is a hook?

A hook redirects a game or graphics function through mod code. This project uses hudhook for DX11 rendering and MinHook for one researched animation consumer. The mod calls the original animation function after it captures the batch.

What is a frame?

A frame is one call to Observer::render from the DX11 overlay loop. Game updates and worker polls do not have to line up one-for-one with rendered frames.

What are pointer chains, mutexes, generations, and monotonic time?

A pointer chain follows addresses stored inside game objects until the reader reaches the player or enemy data it needs. A mutex lets either the worker or renderer use shared cue state for a short time, but not both at once. A generation is a number that changes when old state becomes unsafe, so the renderer can reject it. Monotonic time is a process-local clock that only moves forward and is safe for measuring age.

What is an event in this project?

The word has two nearby meanings. The hook observes a completed animation batch. attack_events::Tracker then records when a continuous animation clock crosses known activation and deactivation times. Neither meaning implies damage or a successful deflect.

What is a model ID?

A model ID identifies an enemy family, such as 1550 for code displayed as c1550. npc_param can select a more specific behavior variation within the same model.

What is an occurrence?

The timing engine increments occurrence whenever continuity breaks. A target, owner, animation, backwards clock, or large timestamp gap can start a new occurrence. The raw ring sequence is not trusted as attack identity.

Why are there two freshness windows?

The main cue path uses 50 ms for lock and animation evidence. The separate effect-research history uses 100 ms. The two systems answer different questions and do not authorize each other.

The safest way to extend the mod

First decide whether the new fact belongs to capture, raw attack classification, alert presentation, practice eligibility, or drawing. Add it at that boundary, then prove it with the matching regression suite. Avoid making the HUD decide game facts or making a memory writer depend on visible labels.
